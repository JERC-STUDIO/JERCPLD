## 8. 2026-11-13 17:0x：开箱根因（区块缓存）与 129 修复

### 8.1 结论（先回答问题：客户端在该坐标看到的是什么）

- 目标方块：原版箱子（用户确认），坐标 `(-1335,64,7909)`，区块 `(-84,494)`。
- 失败会话里，客户端 **没有收到该区块的任何方块数据**：
  - s2c `level_chunk(58)` 只有 1 条目标区块：`sub_chunk_count=0, cache_enabled=true, blobs=1, payload=1B(00)`；
  - 整个会话的 `174 subchunk` 没有任何一条覆盖 `(-84,4,494)`。
- 因此该位置在客户端显示的身份来自 **本地区块缓存**，不是 2193 调色板解出来的 runtime ID。
  “调色板索引错位”不成立：这一段根本没有调色板数据参与。
- 客户端未发 `open_inventory(6)` 的直接原因：它本地认为该位置不是可交互箱子（或方块身份与服务器不一致），所以交互链停在 `mouse_over_entity(33 action=4)` / `item_use_on(36 action=28/29)`。

### 8.2 调色板与 hash 模式

- 2193 `start_game.block_properties = 98`，全部是 `minecraft:*_concrete/wool_stairs/slab`，无自定义方块、无 `minecraft:chest`。
- `block-network-ids-are-hashes=true`：方块网络 ID 是名称+状态的 32 位 hash，不是顺序索引；原版方块（含 chest）不需要出现在 `block_properties` 里，也不存在“服务端列表多 98 项导致索引整体偏移”。
- 参考：`data/generated/block_states.2193.json` 共 22189 条；`minecraft:chest`（`cardinal_direction=south`）hash = `741882976`。
- 98 条新方块（2169 不认识）在 hash 模式下只会被老客户端当作未知方块渲染，不会改变其它方块的 hash/索引；与本次开箱无关。

### 8.3 根因与修复

- 根因：`c2s 129 client_cache_status = true`（真机 16:24 抓包 `81 01 01`）→ BDS 只下发缓存哈希，而 2169 客户端的缓存键/缓存内容与 2193 不一致 → 客户端使用陈旧本地区块。
- 修复：`2169-2193.json` 新增 packet 129 规则，`client_cache_force_off` 强制 `enabled=false`，让 BDS 下发完整区块。
- 隔离/现网模拟验证（1.26.45，protocol 2169）：
  - 修复后 `level_chunk` 变为 `cache=false, blobs=0`，空区块 payload 34B、有方块区块 payload 1064B；
  - 客户端 START_GAME 后正常收到 6–7 个区块，无踢出。
- 注意：真机的 129 在登录时发送；**改完必须重新登录**才生效。
