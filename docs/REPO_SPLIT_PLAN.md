# JERCPLD 仓库拆分与 PTL 模块化计划

> 状态：**已执行，仅第 1 阶段**（2026-11-14）。引擎仓与 PTL 仓已物理分离：
> 规则源与 `JERCPLD.PTL.dll` 构建迁到 [JERC-STUDIO/JERCPTL](https://github.com/JERC-STUDIO/JERCPTL)，
> 本仓只留引擎，安装时用 `install.ps1 -PtlDll <路径>` 带上模块。
> 第 2/3 节描述的「模块带代码、导出处理函数表」ABI **尚未实现**：当前模块仍是纯规则包（数据），
> 复杂结构变换（144/30/148/174/11）仍在引擎里。下文保留为后续方案评估。
> 目标：开源两个仓库——引擎（mod）与 PTL（翻译模块），并保证「新版本只换 PTL 模块」这条契约成立。

- 引擎仓不含任何 `if (proto == 2169)` 之类的版本逻辑。
- PTL 仓不依赖引擎内部符号，只依赖公开 ABI 头文件；不链接 BDS/LeviLamina。

## 2. 兼容性契约（核心）

### 2.1 方向修正

**旧引擎必须能加载新模块**，这是「只换 DLL 支持新版本」的核心。因此：
- ABI 必须**小而稳定**，只提供基础能力；
- 新增版本对时，引擎**零改动**；
- 模块需要的任何新能力，**模块自己实现**，不要求引擎新增导出。

### 2.2 ABI 设计（ABI = 1 起）

模块导出（`extern "C"`，纯 C 类型）：

```c
uint32_t    jercpld_ptl_module_abi_min(void);   // 模块要求的最低引擎 ABI
uint32_t    jercpld_ptl_module_count(void);     // 版本对数量
const char* jercpld_ptl_pair_name(uint32_t i);  // "2169-2193"
int         jercpld_ptl_register(const JercpldHost* host); // 注册处理函数
int         jercpld_ptl_self_check(void);
```

引擎提供（宿主服务表，只增不改字段）：

```c
typedef struct JercpldHost {
    uint32_t abi_version;                 // 引擎提供的 ABI 版本
    void*    user;
    uint8_t* (*buffer_data)(void* buf);   // 可写缓冲区
    size_t   (*buffer_size)(void* buf);
    void     (*log)(void* user, int level, const char* msg);
    int      (*register_handler)(void* user, int from, int to, uint32_t packetId,
                                 int direction, JercpldHandlerFn fn);
    // 后续版本只能“在末尾追加函数指针”，不能改变已有字段
} JercpldHost;

typedef int (*JercpldHandlerFn)(void* user, void* buffer, size_t* payloadOffset, int direction);
// 返回 1 = 已处理；0 = 不处理（引擎保持原样）；-1 = 显式失败（引擎回滚并记录）
```

**边界规则**
- 不跨 DLL 传 STL/C++ 对象、异常、`std::string`。
- 模块不直接调用 BDS 符号；需要协议知识时由模块自带。
- 模块只注册自己支持的 `(from,to,packetId,direction)`；引擎对未注册的包原样放行。

### 2.3 兼容矩阵

| 引擎 ABI | 模块最低 ABI | 结果 |
| --- | --- | --- |
| 1 | 1 | ✅ 加载 |
| 1 | 2 | ❌ 拒绝，日志：`模块需要 ABI 2，引擎提供 ABI 1` |
| 2 | 1 | ✅ 加载（旧模块在新引擎上继续工作） |
| 2 | 2 | ✅ 加载 |
| N | ≤ N | ✅ 加载 |
| N | > N | ❌ 拒绝（安全失败） |

规则：
- 引擎只检查 `module_abi_min <= engine_abi`；不检查上限。
- 模块必须在自己内部处理「引擎 ABI 更高」的情况（只用最低版本保证存在的服务）。
- 规则数据格式另带 `schema_version`；引擎按自己的解析能力接受或拒绝，不影响模块加载的 ABI 判定。

### 2.4 什么情况下必须换引擎

给用户的判据（按顺序）：
1. 新版本是否引入**新的传输层/握手字段**（引擎负责）？是 → 换引擎。
2. 新版本是否引入**新的包 ID 或包方向**（引擎路由表/分派注册）？是 → 换引擎。
3. 新版本的差异是否能由模块内部的代码完成（模块可以带任意 C++ 代码）？能 → **只换模块**。
4. 模块是否只需要引擎已有的宿主服务（缓冲区读写、日志、注册）？是 → 只换模块。
5. 只有「模块需要引擎不存在的**基础设施**」（例如新的加密层、新的压缩算法、新的连接生命周期事件）才需要换引擎；且必须在文档里说明为什么无法在模块内实现。

结论：按这套 ABI，**绝大多数版本差异只需换模块**；引擎只在协议底层/连接层变化时更新。

## 3. 方案对比：A（现状）/ B（模块带代码）/ C（参数化原语）

### 方案 A：维持现状（模块=规则包）

- 引擎：所有 builtin 在引擎里。
- 代价：新版本任何新结构都要改引擎，契约只在「规则能表达」时成立。
- 迁移成本：0。
- 契约满足度：**低**（当前 75% 的包级修复依赖引擎代码）。

### 方案 B：模块带代码（符合契约）

- 模块导出处理函数表，引擎只调度、加载、隔离、统计。
- 迁移成本（估算，按当前 `JerCpldMod.cpp`）：
  - 144 位域/数组/宽松重建：约 330 行；
  - 30 事务内层：约 120 行；
  - 148 item_stack_response：约 120 行；
  - 174 子区块高度图：约 60 行；
  - 11 StartGame/129/198/74/86/180/329：约 300 行；
  - 合计约 **900–1000 行**，占翻译相关代码的绝大多数。
- 风险：同一进程内的模块崩溃无法完全隔离（见第 6 节）；热替换需要「无在线会话」门禁。
- 契约满足度：**高**（新增版本只换模块，引擎不动）。

### 方案 C：引擎参数化原语 + 模块组合（折中）

- 引擎把「可变长位域」「定长前缀 + array<enum> + 尾部定长」「可选字段组丢弃」「游标程序」「固定偏移清零」做成参数化原语；模块用 JSON/描述符组合。
- 可覆盖：144（位域+数组+尾部定长）、11（checksum 清零）、129、111、13、44、198（尾部裁剪）——约 **60–70%** 的现有特例。
- 无法覆盖：30/148（物品描述符嵌套）、74/86（可变字符串列表）、174（子区块版本）——必须写代码。
- 迁移成本：中等（原语接口 + 描述符 schema，约 300–400 行）；契约满足度：**中高**。

### 建议

1. **现在不动架构**：26.45 还在「能正常玩」的调试中期，立即重构会拖慢主线；先把 144/30 修到可玩。
2. 26.45 稳定后，按 **C → B** 两步走：
   - 第一步（C）：把 144/11/129/198/111 参数化，减少引擎特例；
   - 第二步（B）：把 30/148/74/86/174 搬进模块，完成「只换模块」契约。
3. 仓库拆分在 C 完成、B 启动时执行（见第 5 节）。

## 4. 发布与安装

### 产物

- 引擎：`JERCPLD.dll`（mod）+ 配置。
- PTL：`JERCPLD.PTL.dll`（一个或多个模块），放 `plugins/JERCPLD/PTL/`。

### 用户升级判断表

| 场景 | 操作 |
| --- | --- |
| 新增客户端版本，差异是字段增删/枚举 | 只换 PTL 模块 |
| 新增客户端版本，差异是复杂结构（物品/位域/子区块） | 只换 PTL 模块（模块内自带代码） |
| 传输层、握手、压缩、连接生命周期变化 | 换引擎 + 对应模块 |
| 引擎 ABI 升级但模块最低 ABI ≤ 引擎 | 只换模块或都不换 |
| 模块最低 ABI > 引擎 | 必须换引擎（日志会写明） |

### 版本号与 tag

- 引擎 `1.x.y`，PTL 模块 `A.B.C`；模块声明 `module_abi_min`。
- tag：引擎 `engine-v1.2.0`；模块 `ptl-2169-2193-v1.0.0`。
- 兼容声明写进 Release Notes：`engine 1.2 supports module abi_min <= 1`。

## 5. 协作与社区

### 贡献流程（PTL 仓）

1. Fork PTL 仓，新建 `pairs/<a>-<b>/`。
2. 写规则/代码 + `samples/`（真实抓包 hex，脱敏）。
3. 跑 `ptl-selftest`（不依赖 BDS）：A→B→A 往返、边界样本、非法输入。
4. PR 附：版本对清单、样本来源、失败回滚说明。
5. 维护者用引擎的模拟端做端到端回归后再合并。

### 许可证建议

- 引擎：Apache-2.0（专利授权、适合基础设施工厂）。
- PTL：**Apache-2.0**（与引擎一致）。理由：模块要链接引擎 ABI 头、共享安全边界；更宽松的 MIT 也可以，但会让「引擎专利授权覆盖不到模块」的边界变模糊。若社区强烈要求，可对纯规则 JSON 采用 CC0，代码仍 Apache-2.0。

### CI

- 引擎仓：Windows MSVC 构建 + 符号解析自检 + 模拟端回归（2169/2225）。
- PTL 仓：**不依赖 BDS**：用引擎的 `ptl-selftest` 静态库/模拟宿主跑单元测试；覆盖每个包的双向转换、边界、回滚。
- 两仓用 submodule 或 Release 依赖：PTL CI 拉引擎的 `ptl-abi.h` 头文件（只读）。

## 6. 崩溃隔离的现实约束

- 同一进程内加载的模块，**无法做到进程级隔离**。
- 能隔离的：
  - C++ 异常：引擎在调用点 `try/catch`（项目已用 `/EHa`）；
  - 访问违例（AV）：可用 SEH `__try/__except` 捕获，回滚当前包并禁用该模块（建议）；
  - 模块返回错误：安全失败，不影响其他模块。
- 不能隔离的：
  - 栈溢出、堆破坏、死锁、无限循环（会拖死服务端线程）；
  - 模块直接调用未导出符号/破坏引擎状态；
  - 模块在 DLL 卸载时的静态析构异常。
- 结论：**模块必须被当作「可信代码」**；文档要明确写「安装第三方 PTL 模块 = 信任其代码」，并提供「加载前自检 + 失败禁用 + 无在线会话才热替换」三道防线。
